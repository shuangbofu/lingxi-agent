# 项目关系扫描

## 目的
扫描当前项目与候选项目之间的真实关系，并把有证据的关系按“单条项目关系边”保存为待审核知识。

## 扫描策略
本任务关注“有证据的项目关系边”，不是对候选项目做机械全量扫描。Agent 应根据当前项目、候选项目和已有关系说明，选择最能证明关系的代码、配置、依赖文件、接口定义、README、构建文件、OpenAPI、Feign/RPC/MQ 配置等证据。

- 按候选项目逐个判断关系；A 与 B、A 与 C 是两条独立关系，应分别形成独立知识。
- 每条关系都需要具体证据，不能只靠项目名、包名相似或用户配置。
- 保存前按源项目、目标项目、关系类型和关键证据检索项目知识查重。
- 确认新关系时保存为 `PROJECT_RELATION`，保存后默认待审核。

## 识别范围
- 前端后端关系：前端路由/API client/请求 baseURL/接口路径指向后端 Controller。
- SDK 引用关系：Maven/Gradle/npm/go mod 等依赖了候选项目产物、包名或模块名。
- 服务间调用关系：HTTP/RPC/Feign/Dubbo/gRPC/MQ/job/webhook 等调用链。
- 数据关系：共用表、共享业务 ID、上下游状态同步。
- 公共库关系：common、starter、client、api、domain 等共享模块。

## 保存要求
- 类型使用 `PROJECT_RELATION`。
- title 格式建议：`项目A > 项目B：关系类型`。
- keywords 包含两个项目名、关系类型、关键接口/包名/表名。
- content 必须沉淀成“后续分析可直接复用的项目关系知识”，至少包含：
  - `关系结论`：说明谁依赖/调用/消费谁，关系方向是什么。
  - `业务或技术含义`：说明这条关系代表什么协作边界、能力复用、数据流或调用链，不要只说“存在引用”。
  - `关键链路`：用中文概括从入口到目标项目的主要代码/配置链路，可以点名关键类、接口、依赖坐标，但必须解释它们的作用。
  - `后续分析怎么用`：说明排查问题、变更影响、部署顺序、接口联调或回归验证时如何利用这条关系。
  - `置信度与边界`：说明置信度高/中/低以及尚未确认的边界。
- content 按关系复杂度充分展开；证据很多时不要压缩正文，而是把原始依据放到 evidence。
- evidence 写具体文件路径、依赖坐标、接口路径、配置项、包名或表名。
- 每次只保存一条关系边，附带结构化关系参数：
  - `--relation-source-project-id`：调用方、依赖方、入口方或当前判断出的关系源项目 ID。
  - `--relation-target-project-id`：被调用方、被依赖方、服务提供方或当前判断出的关系目标项目 ID。
  - `--relation-type`：简短关系类型，例如 HTTP 调用、前端访问后端、Maven 依赖、共用业务 ID、共享表、MQ 订阅。
- 如果关系是双向的，必须分别保存两条关系边；如果只是展示视角不同，不要反向重复保存同一条关系。

## 最终输出
最终回答必须使用 Markdown 二级标题，标题要根据本次扫描到的项目关系生成。
根据实际情况围绕新增关系、已存在关系、未确认关系、审核关注点组织；标题中尽量带上项目名或关系类型，避免空泛分类。
根据扫描复杂度选择标题数量；没有确认到关系时可以短，但要说明扫描范围和未确认原因。
如果扫描过程中读取了多个项目、多个入口或多类证据，最终回答不能只写保存结果，应保留足够关系证据摘要，让读者能看出“源项目 -> 目标项目 -> 关系类型 -> 关键链路 -> 证据边界”的判断过程。可以省略原始命令过程，但不能省略支撑关系成立或不成立的关键事实。

## 任务边界

只处理系统生成的任务上下文；普通用户问题不应该直接进入该任务。

- 不保存无证据关系。
- 不把候选关联项目当成已确认关系。
- 不把多个目标项目、多条方向不同的关系、多个关系类型混在同一条 `PROJECT_RELATION` 知识里。
- 不用英文保存 relation-type。
