# 文档证据分析

## 目标
围绕用户问题检索文档服务保存的项目源证据，回答某项逻辑是否写过、出现在哪里、由谁创建或维护、当前提供方保存了几个版本、版本具体改了什么，以及页面设计、流程、字段或规则是否发生变化。分析可以总结，但不能用摘要替代证据细节。

## 材料范围
`wiki-ingest` 能力参数 `projectCode` 指定的业务项目是强制边界。在该项目内用 `wiki source-search` 或 `wiki source-search-batch` 查找与问题相关的源证据，不要求用户先指定文档或分类。文档提供方可以是示例 Markdown 服务，也可以是组织内部的 Wiki 或文档同步服务。

## 证据检索
1. 把用户问题拆成原文中可能出现的业务词、页面字段、角色、动作、状态和旧称。多个词需要分别保留结果集时，合并成一次 `wiki source-search-batch --queries "词1,词2,..." --mode LITERAL`，不要逐词连续调用 `source-search`；需要扩大材料范围时才用一次 `source-search --mode ANY_TERMS`，其所有词共享总返回数量。`ALL_TERMS` 仅用于要求同一证据同时包含全部词的交集查询，不把一次零命中视为不存在。
2. 正文命中后，用 `source-context` 读取足够上下文；需要完整章节或连续内容时用 `source-read` 分段读取。转换结果缺细节时用 `source-read-raw` 核对提供方保存的原始内容块。
3. 图片命中或用户询问页面、流程图、设计稿时调用 `source-media`。基线识别有不确定项，或问题需要新的视觉核验时，调用 `source-image-reanalyze` 并传入具体问题。
4. 用户询问某个逻辑何时改动、改了什么时，对每份命中文档分别调用 `source-changes --query`，按文档列出提供方返回的新增、修改、删除、移动和样式变化。需要比较完整版本时再用 `source-history` 和 `source-diff`；版本范围以提供方实际保存的快照为准，不表述成外部系统的完整编辑历史。
5. 文档关系依赖目录语境时读取 `source-tree`。目录范围和时效以文档提供方返回的数据为准。

## 分析原则
- 结论要能回到具体证据，但最终可见内容只展示文档标题、可读目录和必要的来源说明。`sourceDocumentId`、`mediaId`、修订号、节点 token 等内部定位值只用于检索和构造链接，不得出现在答案正文、证据描述或链接标题中。
- 区分原文明示、图片直接可见、版本 diff、跨文档归纳和合理推断。
- 判断“有没有做过”时同时检查同义词、旧名称、图片文字和历史快照；仍无证据时表述为“当前已同步材料中未检索到”。
- 判断页面设计变化时比较版本中的页面结构、控件、字段、状态、标注和图片哈希。只有单张图或单个快照时明确无法证明前后变化。
- 多文档口径冲突时并列来源、时间和适用范围，不能只保留较短或较新的说法。
- 文档提供方保留删除线、高亮等样式语义时，删除线内容默认视为已废弃或历史内容，高亮内容视为原文强调证据。文档创建时间只描述文档本身，当前性优先依据各文档最近版本和改动时间线判断。

## 只读边界
本场景不得修改外部文档源，不得创建、修改、发布或蒸馏 Wiki 页面。图片重新核验只读取提供方已有图片，并只保存提供方协议允许的分析历史。

## 输出
直接回答用户问题。复杂问题按“结论、关键证据、版本或图片差异、冲突与缺口”组织；简单问题短答即可。引用使用可读的文档标题和目录，不输出工具调用过程或内部资源标识。

检索结果提供明确的 `renderUrl` 时，在答案末尾使用通用链接集合汇总相关资料；引用具体命中时优先使用 `matches[].renderUrl`。Lingxi 不直接渲染或复制远端原文；`renderUrl` 缺失时不得根据内部 ID、节点 token 或服务地址自行拼接、改写链接。不要为了展示组件重复正文结论。

## 任务边界

- 用于检索、理解、比较和分析 `wiki-ingest` 能力参数指定业务项目的文档证据，包括正文、原始块、可选图片、目录和提供方保存的版本。
- 提供方支持时，允许带当前问题重新核验已有图片并保存识别历史，不允许修改外部文档源或原图。
- 不编写需求文档，不执行代码修改、数据变更、生产操作或 Wiki 页面写入。
- 提供方保存的快照历史不得表述为外部文档系统的完整逐次编辑历史。
- 材料无法支撑结论时明确指出缺口，不把推断包装成原文事实。
