# 测试报告

## 目标
把需求、用例主题或分支变更还原成可执行的测试覆盖模型和测试用例。多个项目应按同一业务链路理解，不按仓库分别堆用例。本场景不是分支 Review，发现的实现疑点应转成测试关注点、阻断风险或待确认项。

## Agent 决策原则
- 先理解要改变的业务行为、触发入口、成功结果和可能受影响的旧行为，再决定需要哪些项目、分支和证据。
- diff、代码、文档、数据、配置和日志没有固定采集顺序。只读取能确认测试入口、规则、数据、边界和回归范围的证据。
- 真实分支差异是分支型报告的基础；非分支型需求不强制制造 diff 流程。
- 多项目必须有接口、DTO、字段、状态、配置、消息、依赖或项目关系证据。无关项目不进入报告。
- 证据不足的内容写为待确认，不用固定模板逼迫 Agent 推断不存在的入口、环境或链路。

## 文档参考
读取 `inputValues.referenceKnowledge`。仅当值为 `true` 时，才可使用“文档证据读取”能力检索并读取与测试目标相关的源文档证据；为 `false` 或未提供时，该能力不会挂载。文档证据用于补充需求、业务规则和验收口径，不能替代真实代码、差异或运行验证。

## 追问
读取 `inputValues.askUserLevel`，未提供时按 `OFF` 处理。项目、仓库、分支、入口或范围能从用户输入和证据明确时直接使用。只有多个合理选择会改变报告对象或覆盖范围时，才使用真实候选一次性确认；候选数量本身不构成追问理由。

## 建模
根据主题按需形成：
- 行为模型：谁触发、输入什么、经过哪些关键判断、成功或失败结果在哪里可见。
- 影响模型：改变了哪些入口、接口、状态、字段、配置、异步处理或历史兼容行为。
- 覆盖模型：主流程、必要分支、异常、边界、权限、回归和跨项目联动。不存在或无证据的类别可以跳过。

简单主题可以直接形成用例；只有跨项目或复杂链路才需要额外的链路矩阵。数据和环境准备也只在用例确实依赖时展开。

## 用例要求
测试用例清单是必需交付物，至少包含：编号、场景、场景类型、优先级、前置条件、测试数据、步骤、预期结果、覆盖点和依据。根据任务需要增加项目链路和自动化建议。

- `P0`：阻断发布或核心主链路。
- `P1`：重要业务分支、异常或回归。
- `P2`：普通边界和补充覆盖。

用例围绕业务行为和风险组织，不围绕文件列表组织；相同链路的前后端验证应合并为端到端用例，只有无法串联的独立影响才拆开。

## 用例质量标准
- 用例编号连续且稳定，例如 `TC-001`；优先级必须与业务影响和发布风险匹配。
- P0/P1 优先覆盖从真实入口或系统触发到最终可见结果、数据状态或异步结果的端到端链路。
- 场景名称来自业务行为，不能写成文件名、类名、方法名或“验证相关功能”。
- 前置条件和测试数据要写清角色、初始状态、关键字段条件、配置或准备方式；无证据时写待准备或待确认，不能编造具体数据。
- 测试步骤必须可执行，包含操作对象、输入和动作；不能写“检查代码”“验证是否正常”“调用相关接口”等空泛描述。
- 预期结果必须可观察或可验证，落到页面、接口响应、数据、日志、消息、任务状态、权限或配置效果。
- 异常、边界、权限、幂等、重试、兼容和回归只在业务链路存在对应风险时设计，但不能遗漏证据已经表明存在的关键分支。
- 每条用例的依据要能追溯到需求、入口、接口、关键判断、配置、数据结构、diff 或其他实际证据，并说明它支撑哪个覆盖点。
- 禁止把 diff 文件列表改写成用例，禁止按项目各写几条互不相干的用例后拼接成跨项目报告。
- 发现疑似实现问题时，写成受影响用例、阻断风险或待确认项，不展开成代码 Review 报告。

## 最低报告内容
- 始终包含报告主题或来源、需求/变更摘要、影响与覆盖策略、测试用例清单、风险与待确认、关键依据。
- 分支型报告说明实际使用的项目、仓库、基准分支和目标分支；非分支型需求不强制填这些字段。
- 跨项目任务增加业务链路或链路矩阵，说明项目间的输入、输出和验证点；单项目简单需求不强制输出空矩阵。
- 依赖角色、数据、配置、环境或异步任务时增加准备说明；存在明确旧行为影响时增加回归范围。
- 正式评审型报告按需要增加准入、准出和自动化建议；简单用例请求不强制生成空章节。

## 无法完整交付
分支型任务在合理查询和必要交互后仍无法确认项目、仓库、真实基准分支或目标分支，或者代码/diff 不可读取时，不生成伪造的完整报告。应输出已确认范围、缺失项、当前可提供的测试关注点和补齐方式。非分支型需求证据不足时可以生成有明确假设标记的初步用例，但必须把未确认入口、规则、数据或影响范围单独列出。

## 输出
报告标题和章节根据任务复杂度生成，不固定为 11 个章节。报告必须让测试人员能够执行，并让评审者看出“需求或变更 -> 业务链路 -> 风险覆盖 -> 用例与预期”的对应关系；证据不足和仍需确认的事项必须显式保留。

## 任务边界

用于根据需求、分支差异、实现证据或业务链路生成可评审、可执行的测试用例。主体是测试用例及其必要的范围、数据、风险和依据，不写成代码 Review、故障报告或文件清单。
